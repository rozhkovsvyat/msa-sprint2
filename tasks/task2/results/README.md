# Задание 2. Новые сервисы бронирования

Бронирование выносится из монолита по плану [ADR-001](../../task1/results/ADR-001-strangler-booking.md). Код монолита не менялся: создание и список бронирований он передаёт в booking-service через готовый gRPC-прокси, который включается переменной окружения `BOOKING_SERVICE_EXTERNAL_HOST`.

| Компонент | Что это |
| :- | :- |
| [booking-service](../booking-service) | C#, .NET 10. gRPC по [`booking.proto`](../booking.proto) на порту 9090, служебный HTTP на 8080 (`/ping`, `/ready`, `/version`). Своя PostgreSQL. Пользователя, отель, отзывы и промокод проверяет через REST монолита, правила цены перенесены без изменений. Бронирование и событие о нём пишутся в одной транзакции (transactional outbox) |
| [booking-history-service](../booking-history-service) | Читает топик `booking-events` и ведёт историю и статистику по пользователям, отелям и дням в своей PostgreSQL. Аналитики читают её отдельной ролью `analyst` только на чтение |
| [Контракт события](../contracts/booking-events.asyncapi.yaml) | `BookingCreated` в AsyncAPI: версия схемы 1, ключ сообщения — id бронирования |
| [Ops-джоба](../migration/migrate-bookings.sh) | Перенос бронирований при переключении и обратно при откате, со сверкой количества и контрольной суммы |
| [Стенд](../docker-compose.yml) | Монолит с прокси, три PostgreSQL, Kafka и ZooKeeper из задания, ops-джоба и регресс |
| [Регресс](regress.sh) | Доработанный `test/regress.sh`: фикстуры переносятся той же ops-джобой, полный список бронирований читается служебным gRPC-методом с токеном, проверяется отказ без токена и пустой `userId`, у отказов проверяется причина, новые бронирования ищутся в истории |

## Запуск

```bash
docker network create hotelio-net   # если сети ещё нет
cd tasks/task2
docker compose up -d --build --wait booking-service booking-history-service monolith
docker compose run --rm --build regress   # регресс курса через монолит с прокси
```

Если стенд поднимали до 01.11.2026 и в таблице `dead_letter` сервиса истории остались сообщения, миграция `0002` не даст сервису запуститься: разберите их или поднимите стенд с чистыми томами (`docker compose down -v`).

Схемы новых БД создают сервисы `booking-schema` и `history-schema` (команда `migrate` из образов сервисов) до запуска самих сервисов. Пароли — демо-значения стенда, их можно переопределить переменными окружения или файлом `.env`.

На чистом стенде переносить нечего, поэтому регресс сам загружает фикстуры в БД монолита и переносит их ops-джобой с флагом `--reset-target` (он очищает БД сервиса и нужен только тестовому стенду). Если остановить booking-service, тесты бронирования падают, как и ожидается в задании, а запросы бронирований через монолит возвращают 500 (test-log.txt, части 1 и 3):

```bash
docker compose stop booking-service; docker compose run --rm regress; docker compose start booking-service
```

## Стратегия миграции данных

Готовый прокси отправляет в booking-service не только создание, но и список бронирований, причём сразу весь трафик. Значит, после переключения пишет только сервис, а старые бронирования должны оказаться в его БД, иначе список через монолит их не покажет. Постоянной синхронизации нет: в каждый момент пишет одна сторона, а откат — разовая операция.

1. Окно переключения: монолит и booking-service остановлены, бронирования в это время никто не пишет. `MIGRATION_OFFLINE=yes` — подтверждение оператора, сам скрипт процессы не останавливает.
2. Перенос (`migrate-bookings.sh forward`): таблица `booking` копируется с теми же id, счётчик id сервиса сдвигается за максимальный. Источник только читается, приёмник пишется одной транзакцией, повторный запуск не создаёт дублей.
3. Пустые даты: монолит не заполняет `created_at` у бронирований, созданных через API, а прокси не принимает пустую дату. Таким записям ставится время переноса и флаг `created_at_estimated = true`.
4. История: для перенесённых бронирований в outbox пишутся события `BookingCreated` с `source = migration`. Id события выводится из id бронирования, поэтому повторный перенос не создаёт новых событий.
5. Сверка: количество и контрольная сумма неизменяемых полей должны совпасть в обеих БД, иначе джоба завершается с ошибкой и переключение не продолжается.
6. Включение: запускаем booking-service, затем монолит с `BOOKING_SERVICE_EXTERNAL_HOST=booking-service`.

Переключение на существующих данных (до этого монолит работал с `BOOKING_SERVICE_EXTERNAL_HOST=false`):

```bash
docker compose stop monolith booking-service
docker compose build
docker compose run --rm -e MIGRATION_OFFLINE=yes booking-migration forward  # схема, перенос, сверка; дальше — только при коде 0
docker compose up -d booking-service booking-history-service
docker compose up -d monolith                                                # прокси включён значением из .env
```

Откат: команда `reverse` дописывает в монолит бронирования, созданные после переключения, с теми же id и сдвигает его счётчик. С `BOOKING_SERVICE_EXTERNAL_HOST=false` монолит снова работает сам: бин прокси создаётся только при включённой настройке (`@ConditionalOnProperty`).

```bash
docker compose stop monolith booking-service
docker compose run --rm -e MIGRATION_OFFLINE=yes booking-migration reverse
BOOKING_SERVICE_EXTERNAL_HOST=false docker compose up -d monolith
```

Весь цикл «перенос → новое бронирование → откат → повторный перенос» на чистом стенде прогоняет [`migration/cutover-drill.sh`](../migration/cutover-drill.sh), лог — [cutover-drill-log.txt](cutover-drill-log.txt). Окно переключения заняло 8 с вместе с перезапуском монолита, откат — 6 с. Время переноса растёт с размером таблицы, поэтому на боевом объёме его нужно замерить на копии БД; если окно окажется недопустимым, следующий вариант — CDC (альтернативы в ADR-001).

Во время этих учений нашлась проблема монолита: в `application.yml` стоит `ddl-auto: create`, и перезапуск при переключении стирал пользователей, отели и бронирования. В compose настройка переопределена окружением `SPRING_JPA_HIBERNATE_DDL_AUTO=update`, код монолита не менялся.

## Стратегия To-Be

Целевое состояние через два месяца и через год описано в ADR-001. Следующие шаги для бронирования:

- личный кабинет читает бронирования из booking-service через GraphQL (задание 3), затем и остальные клиенты ходят в сервис через шлюз, а не через монолит;
- сервис выпускается Helm-чартом из CI (задание 4), новые версии — канарейкой в Istio (задание 5);
- после стабилизации — ключ идемпотентности для создания и исправление дефектов, которые перенесли как есть (скидка как сумма, ответ 500 на бизнес-отказ);
- прокси монолита заменяется своим кодом, `promo_code` в контракте становится `optional`, архивная таблица `booking` в монолите удаляется.

## Ограничения готового прокси

- `GET /api/bookings` без `userId` через монолит падает с 500: прокси вызывает `BookingListRequest.setUserId(null)` ещё до обращения к сервису (конец [listing-rest-vs-grpc.txt](listing-rest-vs-grpc.txt)). Полный список поэтому читают не через монолит, а служебным методом booking-service — тесты бронирований задание разрешает менять.
- `GET /api/bookings?userId=` с пустым параметром прокси передаёт сервису пустой строкой. Сервис отвечает пустым списком, как монолит без прокси: публичный метод чужие бронирования не отдаёт. Полный список — служебный метод `booking.admin.BookingAdminService/ListAllBookings`, контракт [`booking-admin.proto`](../booking-admin.proto): токен в метаданных `authorization: Bearer …`, страницы до 500 строк по возрастанию `id`, без токена — `UNAUTHENTICATED`. Так список читают регресс, сверка при переносе и разбор инцидентов. Когда прокси заменим своим кодом, запрос без `userId` пойдёт в тот же служебный метод.
- `promo_code` в `booking.proto` — обычная строка proto3, поэтому монолит отдаёт `"promoCode": ""` вместо `null`.
- Бизнес-отказ сервис возвращает как gRPC `FAILED_PRECONDITION` с причиной, но монолит по-прежнему отвечает клиенту 500 без текста.
- Прокси не передаёт сервису `x-request-id` исходного HTTP-запроса, поэтому на этой границе создаётся новый идентификатор.

## Надёжность

- Бронирование и событие пишутся одной транзакцией (transactional outbox), фоновый publisher отправляет событие в Kafka. Пока Kafka недоступна, событие ждёт в outbox и уходит после её восстановления ([delivery-check.log](delivery-check.log)). Событие, которое повтором не отправить (например, слишком большое), уходит в карантин (`dead_lettered_at`) и не держит очередь; состояние очереди — `GET /diagnostics/outbox`. Опубликованные события старше 14 дней удаляет отдельный фоновый процесс сервиса, пакетами по 1000 строк. Срок дольше, чем Kafka хранит `booking-events` (7 дней): после долгого простоя потребителя событие можно отправить заново из outbox. Outbox сделан без MassTransit и CAP: событие одно, а своя отправка — около 120 строк, которые легко прочитать и проверить тестами.
- Kafka доставляет «хотя бы один раз», поэтому booking-history-service фиксирует смещение после записи в историю, а повтор отбрасывает по `event_id`. Сообщение, которое не удалось обработать (не разбирается или его данные отвергает PostgreSQL), уходит байт в байт в топик `booking-events.dlq`: причина и исходная позиция — в заголовках `dlq-reason`, `dlq-topic`, `dlq-partition`, `dlq-offset`. Смещение фиксируется после того, как Kafka приняла сообщение в DLQ, и чтение топика продолжается. Если недоступна сама БД истории (нет связи, неверный пароль, нет прав), смещение не фиксируется и сообщение читается снова.
- Форматы REST монолита знает только модуль `Legacy` (Anti-Corruption Layer): он переводит ответы монолита в модель бронирования. Например, 404 на пользователя сервис считает неизвестным пользователем и отказывает с «User is inactive», 400 на промокод — отсутствием скидки, а пустой или неполный ответ — недоступностью монолита (gRPC `UNAVAILABLE`). На все обращения к монолиту при создании одного бронирования отведено 3 с; GET повторяется один раз, POST проверки промокода не повторяется, при потоке ошибок срабатывает circuit breaker (стандартный resilience handler .NET).
- Схема БД создаётся SQL-миграциями (DbUp) командой `migrate` того же образа до запуска сервиса; пока схема не готова, `/ready` отвечает 503.
- `x-request-id` передаётся в вызовы монолита, в событие и в историю (`correlation_id`).
- Настройки приходят из окружения (`BOOKING_DB`, `HISTORY_DB`, `MONOLITH_URL`, `KAFKA_BOOTSTRAP`; необязательные `KAFKA_DLQ_TOPIC` — по умолчанию имя топика с суффиксом `.dlq`, `OUTBOX_RETENTION_DAYS` — по умолчанию 14 и `BOOKING_ADMIN_TOKEN` — без него служебный список закрыт всем). На стенде значения лежат в [`.env`](../.env), в бою токен и пароли приходят из хранилища секретов. В кластере заданий 4–5 нет Kafka, там публикация выключается `OUTBOX_PUBLISHER=disabled`; `FAULT_INJECTION_STATUS` нужен только для проверки fallback в задании 5.

В пайплайне задания 4 это джобы `test:unit` и `test:integration`, а регресс курса на чистом стенде — `test:api`.

Что чем проверяется. Набор шёл от того, что обещает ADR: поведение как в монолите, перевод ответов монолита, доставка «хотя бы один раз» без потерь и дублей, перенос с откатом. Интеграционные тесты проверены от обратного: если сломать то, что тест защищает (разделить транзакцию, убрать защиту от дублей, подтвердить смещение до записи, не отправить сообщение в DLQ или отправить туда событие при неверном пароле к БД истории, удалить при очистке неотправленное событие), он падает.
