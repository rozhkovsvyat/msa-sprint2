# Использование ИИ

Работа подготовлена Святославом Рожковым с использованием ИИ-агентов. Код, конфигурации и тексты генерировали агенты по задачам и решениям Святослава; он разбирал результат, оспаривал решения и принимал работу. Вклад разделён следующим образом.

| Часть работы | Вклад Святослава | Вклад ИИ |
| :- | :- | :- |
| Первый модуль | Согласился начать с бронирования: от него в монолите никто не зависит, а точка переключения уже есть — готовый gRPC-прокси | Разобрал код монолита, jar прокси и стенд, нашёл дефекты и расхождения с описанием (Н1–Н11 в ADR-001), подготовил ADR и схемы C4 |
| Стек и сервисы | Выбрал C#/.NET вместо предложенной ИИ Java | Написал booking-service и booking-history-service, доработал регресс курса |
| Перенос данных | Выбрал перенос ops-джобой с остановкой записи — по своему опыту переноса данных — и откат той же джобой; задал критерии отката по доле ошибок и задержке относительно базовой линии | Нашёл, что монолит не заполняет дату бронирования; написал джобу со сверкой и учения по переключению и откату |
| События | Согласился на transactional outbox; перевёл dead letter из таблицы в топик Kafka и попросил очистку outbox отдельным фоновым процессом | Предложил outbox, написал отправку в Kafka, сервис истории, DLQ и очистку |
| Тесты и пайплайн | Задал набор тестов и устройство пайплайна по своему рабочему проекту: юнит-тесты, интеграционные тесты, регресс курса как API-тесты в пайплайне, ручной выпуск в prod; выбрал Shouldly, Moq и AutoFixture | Предложил поднимать зависимости интеграционных тестов через Testcontainers и отстоял это в споре; написал тесты, джобы и скрипты проверок, выполнил прогоны |
| Личный кабинет | Попросил перепроверить, правда ли у отелей нет названий, и выбрал `null` вместо выдуманных значений; выбрал `@override` по схеме задания | Проверил данные монолита, нашёл, что шлюз сам не передаёт заголовки подграфам; написал шлюз, три подграфа и тесты |
| Kubernetes и Istio | Согласился с `failoverPriority` после того, как ИИ объяснил, почему повтор внутри subset v1 не переведёт запрос на v2 | Написал Helm-чарты, манифесты Istio и проверочные скрипты, выполнил прогоны |
| Проверка | Разобрал работу на вопросах, оспорил спорные решения и формулировки, поручил ревью и отвечает за принятые решения | Объяснял решения, провёл ревью другими моделями, сверил отчёты с кодом и логами |

Например, Святослав не согласился оставить описанным ограничением то, что через прокси монолита `GET /api/bookings?userId=` отдаёт бронирования всех пользователей, и потребовал исправить: теперь публичный список отдаёт только свои бронирования, а полный список — служебный метод с токеном администратора и постраничным выводом. Он же решил хранить сообщения, которые не удалось обработать, в топике Kafka, а не в таблице: при выносе следующих модулей это общий приём, и переделывать не придётся.

Использованы Claude Opus 5.5 для основной работы, Codex и Qwen для части доработки; Fable 5.1 и Codex — для дополнительного ревью. Проверка другой моделью не является независимой экспертизой. Агенты также поднимали стенды и снимали логи и скриншоты для `results`.

## Проработка через объяснение и возражения

После реализации ИИ составил 36 вопросов по заданиям: сначала объяснял, как и почему сделано, затем спрашивал суждение. Святослав отвечал голосом своими словами, оспаривал решения и сами вопросы, если они были сформулированы неясно; где ответ был неполным, ИИ объяснял место заново.

| Инициатива Святослава | Изменение решения |
| :- | :- |
| Отклонил Java: .NET — его основной стек, задание разрешает любой язык, в заготовках курса уже есть Node.js и Go | Цена решения — второй стек для команды Hotelio — записана в ADR-001 |
| ИИ предлагал оставить в `discountPercent` скидку, сохранённую при бронировании; Святослав выбрал вариант из схемы задания | Поле отдаёт новый подграф промокодов, применённая скидка остаётся в цене бронирования |
| Попросил сверить работу с текстом задания и найти противоречия между отчётами, кодом и логами | Включены Playground и introspection на шлюзе, добавлены запросы через монолит без booking-service и недостающие файлы в `results`; описаны ограничения готового прокси |
| Спросил, почему регресс курса и проверки на стенде — отдельные скрипты, а не тесты в пайплайне | Регресс — джоба `test:api`, учения на стенде — ручные джобы `ops:*` |
| Попросил интеграционные тесты, Shouldly и имена джоб, как в своём рабочем проекте; предлагал поднимать PostgreSQL и Kafka для тестов сервисами пайплайна, но после спора согласился на Testcontainers: тесты нарочно ломают зависимости (замораживают Kafka, подсовывают неверный пароль) и на общих сервисах мешали бы друг другу | Интеграционные тесты outbox на Testcontainers, юнит-тесты на Shouldly, джобы `test:unit`, `test:integration`, `test:api` |
| Предложил покрыть тестом путь, который ИИ предлагал оставить без теста: БД истории недоступна дольше повторов | Тест проверяет, что событие не подтверждено и читается снова |
| Спросил, почему пользователи и отели берутся у монолита по REST, а не из Kafka | Оставили REST, как требует задание: проверки при бронировании нужны на текущий момент |
| Попросил проверить код на слишком подробные комментарии | Описания классов сокращены до одной-двух строк |
| Предложил описать в ADR команду через Kafka с сагой как альтернативу, спросил, почему базовая линия — неделя и как называются показатели, предложил чинить в пределах окна, а отставание истории закрывать хотфиксом | В ADR-001 — новые альтернативы, критерии отката с SLI (доля 5xx, p95), ясное объяснение пустых дат |
| Спросил, чем dead letter в таблице лучше топика, и решил перевести его в DLQ-топик Kafka; попросил фоновую очистку outbox, спросил про матрицу покрытия тестами | DLQ-топик `booking-events.dlq`, отдельный процесс очистки опубликованных событий, тесты на оба, таблица «что чем проверяется» в README задания 2 |
| Возразил против значения переключателя прокси «по умолчанию» в docker-compose | Значение задано в `.env`, без неявной подстановки |
| Не согласился оставлять как ограничение то, что `GET /api/bookings?userId=` отдаёт бронирования всех пользователей, — попросил починить, а не описать | Публичный список возвращает только бронирования запрошенного пользователя, как монолит; полный список отдаёт служебный gRPC-метод `ListAllBookings` с токеном и пагинацией (`booking-admin.proto`), регресс читает список им и проверяет отказ без токена |
| Настоял на готовых библиотеках вместо самописных тестовых заготовок: их знают другие разработчики, и их не нужно поддерживать | Монолит в юнит-тестах подменяется через Moq, случайные тестовые данные даёт AutoFixture; самописные заглушки удалены |

ИИ предложил заменить самописные ограничитель запросов к монолиту и кеш отелей в GraphQL на `p-limit` и `lru-cache` — Святослав согласился.

ИИ сделал каркас решения и рутинную реализацию: код, тесты, скрипты и прогоны. Святослав вёл работу как владелец продукта: выбирал решения на развилках, спорил с теми, что считал неверными, и требовал объяснений там, где реализация была непонятна, — после этого её переделывали. На вопросах он своими словами объяснил стратегию переноса, outbox и доставку событий, защиту от дублей, пайплайн и выпуск в prod; устройство fallback и outlier detection в Istio и частности GraphQL ИИ разобрал с ним отдельно.

## Сверка с заданием и ревью

По поручению Святослава итоговую редакцию сверили с заданием и отдали на ревью другим моделям: на ошибки в коде, глазами ревьюера курса и на качество кода. Автор поручил внести обоснованные замечания: например, ошибки самой БД истории больше не уводят события в DLQ, а читаются снова; ответы подграфов не раскрывают клиенту внутренние ошибки; проверки Istio падают при неверном поведении. Не все замечания приняты: их проверяли по заданию и коду. Проверки другими моделями не гарантируют приёмку курса.

## Что ИИ добавил сверх задания

Эти приёмы предложил ИИ; большинства из них в уроках спринта нет:
- transactional outbox и приём событий без дублей по `eventId` — событие не теряется и не удваивает статистику; dead letter (по решению Святослава — DLQ-топик Kafka) — сообщение, которое не удалось обработать, не останавливает чтение топика;
- resilience handler .NET (Polly) — сервис не добивает медленный монолит; DbUp и команда `migrate` — схема БД создаётся до запуска сервиса; сквозной `x-request-id` — один запрос виден во всех логах;
- в GraphQL — кеш отелей и предел запросов к монолиту поверх DataLoader, ограничение глубины запроса и числа алиасов (graphql-armor) — длинные и тяжёлые запросы не перегружают монолит и шлюз;
- в Istio — `failoverPriority` с outlier detection для fallback, Lua в EnvoyFilter для фича-флага, fortio для проверки circuit breaking;
- в пайплайне — выпуск в prod тем же образом и откат через `helm rollback`.
